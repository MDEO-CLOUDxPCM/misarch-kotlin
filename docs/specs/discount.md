## 1. Role in the system

- Owns `Discount`, `Coupon`, `CouponRedemption` (user claimed coupon), `DiscountUsage` (items bought per user and
  discount) and the "applies to" join tables `DiscountTo{Category,Product,ProductVariant}`.
- Keeps replica tables filled by events: `UserEntity` (`user/user/created`), `ProductEntity` and
  `ProductToCategoryEntity` (`catalog/product/created`), `ProductVariantEntity` (`catalog/product-variant/created`),
  and `CategoryEntity` (`catalog/category/created`). Product category changes are never propagated, because
  `catalog/product/updated` is not subscribed.
- **Synchronous hot path:** during `createOrder`, order calls `POST localhost:3500/v1.0/invoke/discount/method/graphql`
  with `findApplicableDiscounts` (no `Authorized-User` header). This happens once per order on the Gatling buy path.
  `ProductVariant.applicableDiscounts` is the federated read field used when browsing.
- **Saga step:** consumes `inventory/product-item/reservation-succeeded` and checks per-user usage limits. It then
  upserts `DiscountUsage` and publishes `discount/order/validation-succeeded` (consumed by payment and invoice) or
  `discount/order/validation-failed` (consumed by inventory, which releases the reservation).
- Only `discount/coupon/created` has a subscriber (order). `discount/discount/*` and `discount/coupon/updated` have
  none.

## 3. GraphQL schema summary (federation v2.5, `clearDirectives()` in `didBuildSchema`)

- `Query`: `discount(id: UUID!): Discount!`, `coupon(id: UUID!): Coupon!`,
  `findApplicableDiscounts(input: FindApplicableDiscountsInput!): [DiscountsForProductVariant!]! @inaccessible`.
- `Mutation`: `createDiscount`, `createCoupon`, `registerCoupon`, `updateDiscount` and `updateCoupon`. Each takes `input: …Input!` and
  returns `Discount!` or `Coupon!`.
- Entities (`@key(fields:"id", resolvable: true)`, all `implements Node`): `Discount`, `Coupon`, `DiscountUsage`,
  and the stubs `User`, `Product`, `ProductVariant` and `Category`. `_entities` union = `Category | Coupon | Discount | DiscountUsage |
  Product | ProductVariant | User`.
- `Discount`: `id`, `discount: Float!`, `maxUsagesPerUser: Int`, `validFrom/validUntil: DateTime!`,
  `minOrderAmount: Int`, `discountAppliesToCategories/Products/ProductVariants(first, skip, orderBy: CommonOrderInput)`,
  `discountRequiresCoupon(first, skip, orderBy: CouponOrderInput, filter: CouponFilterInput): CouponConnection!`,
  `discountUsages(first, skip, orderBy: DiscountUsageOrderInput)`.
- `Coupon`: `id, code, validFrom, validUntil, usages: Int!, maxUsages: Int, discount: Discount!, users(first, skip, orderBy: CommonOrderInput)`.
- `DiscountUsage`: `id, usages: Int!, user: User!, discount: Discount!`.
- `User`: `coupons(first, skip, orderBy, filter)`, `discountUsages(...)`. `Product`/`Category`: `discounts(first, skip,
  orderBy: DiscountOrderInput)`. `ProductVariant`: `discounts(...)`, `applicableDiscounts(...)`.
- Connections `{Category,Coupon,Discount,DiscountUsage,Product,ProductVariant,User}Connection @shareable` with
  `hasNextPage`, `nodes` and `totalCount`. `DiscountsForProductVariant {productVariantId, count, discounts}`.
- Enums `CommonOrderField {ID}`, `CouponOrderField {ID, VALID_FROM, VALID_UNTIL}`, `DiscountOrderField {ID, VALID_FROM,
  VALID_UNTIL}`, `DiscountUsageOrderField {ID, USAGES}`, `OrderDirection {ASC, DESC}`. Order inputs `{direction, field}`.
- Copy-paste descriptions that must be **kept**: `CommonOrderInput` = "Discount order";
  `Discount.discountRequiresCoupon` = "Get all product variants to which this discount directly applies";
  `UpdateDiscountInput.maxUsagesPerUser` = "The discount applied to the order item."; the "weather" typo in `CouponFilterInput`.
- Nullability quirks: `CreateDiscountInput.maxUsagesPerUser: Int!` and `CreateCouponInput.maxUsages: Int!`, although the DB
  columns are nullable. `UpdateDiscountInput.maxUsagesPerUser`, `UpdateDiscountInput.minOrderAmount` and
  `UpdateCouponInput.maxUsages` are `OptionalInput` (explicit `null` clears the value). All other update fields are plain
  nullable fields, where `null` means "unchanged".
- `misarch/schemas` prints `type DiscountsForProductVariant @shareable`, but the code has no `@ShareableDirective` on
  that class. The **live** SDL of the running original (`reference/sdl/discount.graphql`) also has no `@shareable` there.
  The `@shareable` comes from the schema-transform step of the schemas repository (see `reference/README.md`). The
  port reproduces the live SDL. `tools/sdl-diff.sh discount` is empty, and `--schemas` shows only this difference.

## 4. Resolvers and authorization

`dfe.authorizedUser` throws `IllegalStateException("Unauthorized access")` when the header is missing.
`checkIsEmployee()` throws `IllegalStateException("Unauthorized access: <id> is not an employee or admin")`.
All checks happen **before** the data access, synchronously in the data fetcher.

| Field | Auth | Behaviour |
|---|---|---|
| `Query.discount(id)`, `Query.coupon(id)` | employee | Load through the id dataloader. An unknown id throws an NPE in the batch loader (`entities[it]!!`), which fails **every key in that batch**. **FIXED** (docs/fixes/discount.md Q4): only the unknown key fails (`… : null`). |
| `Query.findApplicableDiscounts` | none | See §6. |
| `createDiscount`, `createCoupon`, `updateDiscount`, `updateCoupon` | employee | See §5. |
| `registerCoupon` | caller is `input.userId`, or employee | See §5. |
| `Category/Product/ProductVariant.discounts` | employee | Discounts **directly** linked by the join table: inner join on the join table, filtered by the stub id. |
| `ProductVariant.applicableDiscounts` | none (optional user) | Condition `applies(pv) AND (noCoupons OR [user != null: EXISTS coupon of d redeemed by user]) AND validFrom <= now AND validUntil >= now`. There is no min-order or usage check. Paginated with `DiscountOrder`. |
| `Discount.discountAppliesTo{Categories,Products,ProductVariants}` | employee | Join table filtered by `discountId`. |
| `Discount.discountRequiresCoupon` | none, but filtered | Coupons with `discountId = id`. **No header → `FALSE` (empty, totalCount 0)**. Employee → all. Other user → only coupons the caller has redeemed. The `filter.userHasCoupon` filter requires a header (`IllegalArgumentException("The userHasCoupon filter requires an authorized user")`); a foreign user id requires an employee. |
| `Discount.discountUsages`, `User.discountUsages` | employee | `DiscountUsageEntity` filtered by `discountId` / `userId`. |
| `Coupon.usages`, `Coupon.maxUsages`, `Coupon.users` | employee | `users` = `UserEntity` inner join `CouponRedemptionEntity` filtered by `couponId`. |
| `Coupon.discount`, `DiscountUsage.discount`, `DiscountUsage.user` | none | Through the dataloader (`UserDataLoader` reads the `UserEntity` replica, so the row must exist). |
| `User.coupons` | caller is the same user, or employee | `CouponEntity` inner join `CouponRedemptionEntity` filtered by `userId`, plus `filter` and the coupon auth filter above. |
| `_entities` | none | `Category/Product/ProductVariant/User` return stubs **without a DB check** (a null id → NPE). `Coupon/Discount/DiscountUsage` load through the dataloader (null id → null entity; unknown id → NPE for the batch). |

**Connections (`BaseConnection`)**: `nodes` = `SELECT <entity cols> FROM T [joins] WHERE <predicate AND filter AND authFilter>
ORDER BY <field exprs…> <dir> LIMIT <first ?: Long.MAX_VALUE> OFFSET <skip ?: 0>`. Ordering fields with a tie-breaker
are `VALID_FROM` → `(validFrom, id)`, `VALID_UNTIL` → `(validUntil, id)` and `USAGES` → `(usages, id)`, all in the same
direction. The default is `ID ASC`. `totalCount` = `SELECT count(T.id) … WHERE …`. `hasNextPage` is `false` if `first == null`.
Otherwise it runs the same select **without ORDER BY**, with `OFFSET first+skip LIMIT 1`, and checks for a row. The three
fields are resolved lazily, so each requested field is one SQL query.

## 5. Mutations (one transaction each; R2DBC tx; events are published **inside** the tx, before commit)

The original annotated `Mutation` with `@Transactional(REQUIRES_NEW)`; here the service method each mutation calls is
`@Transactional`.

- **createDiscount**:
  1. All three id lists empty → `IllegalArgumentException("At least one category, product or product variant must be specified")`.
  2. Existence check per id, one `SELECT … LIMIT 1` each, in this order: categories, products, variants. Errors:
     `"Categories with ids [a, b] do not exist"`, `"Products with ids [..] do not exist"`, `"Product variants with ids [..] do not exist"`.
  3. Range checks: `discount >= 0` ("A discount cannot increase the price and thus must be >= 0") and `discount <= 1` ("A discount cannot be larger than 1").
  4. Insert the discount (id from the DB default `uuid_generate_v4()`) and one INSERT per join row (sets, in input order without duplicates).
  5. Publish `discount/discount/created`.

  `validFrom > validUntil` is not checked. The returned entity is the in-memory one, so the input offset is kept.
- **createCoupon**:
  1. Discount must exist ("Discount with id X does not exist").
  2. `findByCode` must be empty ("Coupon with code X already exists").
  3. Insert `(maxUsages, validUntil, validFrom, code, discountId)`. `usages` is `@ReadOnlyProperty`, so the DB default 0 applies.
  4. Publish `discount/coupon/created`.
- **updateCoupon**: `findById(id).awaitSingle()` (missing → `NoSuchElementException`). Non-null `code`, `validUntil` and
  `validFrom` overwrite. A defined `maxUsages` (possibly null) overwrites. There is no uniqueness pre-check for `code`
  (the DB unique constraint fails instead). Full-row UPDATE without `usages`. Publish `discount/coupon/updated`. The
  response shows `usages` as read before the update.
- **updateDiscount**: `findById` (missing → NoSuchElement). A defined `maxUsagesPerUser` (**null allowed**, see Q3)
  overwrites; non-null `validUntil`/`validFrom` overwrite; a defined `minOrderAmount` overwrites. The `discount` value
  cannot change. Then:
  1. Existence check of the added ids (the same errors as on create).
  2. Insert the added join rows (a duplicate → unique violation).
  3. One DELETE per removed id.
  4. Full-row UPDATE of the discount.
  5. Publish `discount/discount/updated`, with the id lists **re-read from the join tables** (`findByDiscountId` × 3, DB order).
- **registerCoupon**:
  1. `findByCode` (missing → "Coupon with code X does not exist").
  2. Require `validFrom < now < validUntil` (**strict**, unlike the inclusive SQL check for discounts) → "Coupon with code X is not valid currently".
  3. Insert `CouponRedemptionEntity(couponId, userId)`. The DB trigger increments `CouponEntity.usages` and raises
     'Coupon has been used too often' when `usages > maxUsages` (**FIXED** Q10: the increment was not atomic, see §9). A duplicate `(couponId, userId)` → unique violation. An
     unknown user → FK violation.
  4. Re-read the coupon and return it.

  No event is published.

DB errors surface as GraphQL errors carrying Spring's translated exception message. Only the fact that an error occurs
must match, not the exact wording.

## 6. `findApplicableDiscounts` (order → discount, synchronous)

Input `{userId, orderAmount: Int, productVariants: [{productVariantId, count: Int, couponIds: [UUID]}]}`. Order sends
`orderAmount` as i64; values over Int32 fail GraphQL coercion in both versions.

1. `productVariantRepository.findAllById(set)`. Missing →
   `IllegalArgumentException("Product variant(s) with id(s) [..] do(es) not exist")`.
2. For **each** product variant input, sequentially, one query:
   ```sql
   SELECT d.* FROM DiscountEntity d
     LEFT JOIN DiscountUsageEntity du ON d.id = du.discountId AND du.userId = :user
   WHERE ( d.id IN (SELECT discountId FROM DiscountToProductVariantEntity WHERE productVariantId = :pv)
        OR d.id IN (SELECT dp.discountId FROM DiscountToProductEntity dp JOIN ProductVariantEntity v ON dp.productId = v.productId WHERE v.id = :pv)
        OR d.id IN (SELECT dc.discountId FROM DiscountToCategoryEntity dc JOIN ProductToCategoryEntity pc ON dc.categoryId = pc.categoryId
                    JOIN ProductVariantEntity v ON pc.productId = v.productId WHERE v.id = :pv) )
     AND ( NOT EXISTS (SELECT true FROM CouponEntity c WHERE c.discountId = d.id)
        OR d.id IN (SELECT c.discountId FROM CouponEntity c JOIN CouponRedemptionEntity r ON r.couponId = c.id
                    WHERE c.id IN (:couponIds /* empty → 1=2 */) AND r.userId = :user) )
     AND d.validFrom <= :now AND d.validUntil >= :now
     AND (d.minOrderAmount IS NULL OR d.minOrderAmount <= :orderAmount)
   ```
   There is no ORDER BY. The left join has no effect on the result (the unique `(discountId, userId)` constraint allows
   at most one row, only discount columns are selected); the service runs the query without it (§12). `now` is
   evaluated per query.
3. Remaining usages: `findByUserIdAndDiscountIdIn(userId, ids of discounts with maxUsagesPerUser != null)`. An empty
   id set returns nothing. It then computes `remaining[d.id] = d.maxUsagesPerUser!! - usages` for **all** discounts →
   **NPE if any applicable discount has `maxUsagesPerUser = null`** (Q3). **FIXED**: such discounts are unlimited.
4. `couponRepository.findAllById(all couponIds)`. Missing →
   `"Coupon(s) with id(s) [..] do(es) not exist"`.
5. For each product variant input, in input order:
   - `usable = discounts where remaining[id] >= count`.
   - Decrement `remaining[id] -= count` for every usable discount. This map is shared across the variants, so later
     variants see less.
   - Every input coupon's `discountId` must be among the usable ones. Otherwise →
     `IllegalArgumentException("Coupon with id X could not be used, either due to insufficient remaining usages, the user not owning the coupon, or the coupon not being applicable")`.
   - Coupons grouped by discount (with duplicates of the input list) with size > 1 → `IllegalStateException("Coupons with ids [..] are used multiple times for the same discount D")`.
   - Result: `{productVariantId, count, discounts: usable}`, with the DB row order kept.

## 7. Events

### Published (Dapr `pubsub`; payload = Jackson with **`NON_NULL`** (Dapr `ObjectSerializer`), so null fields are **omitted**)

| Topic | When | Payload |
|---|---|---|
| `discount/discount/created` | createDiscount | `{id, discount: Double, maxUsagesPerUser?, validUntil, validFrom, minOrderAmount?, discountAppliesToCategoryIds: [UUID], discountAppliesToProductIds: [UUID], discountAppliesToProductVariantIds: [UUID]}` |
| `discount/discount/updated` | updateDiscount | same shape |
| `discount/coupon/created` | createCoupon | `{id, maxUsages?, validUntil, validFrom, code, discountId}` |
| `discount/coupon/updated` | updateCoupon | same shape |
| `discount/order/validation-succeeded` | validateOrder ok | `{order: OrderDTO}` |
| `discount/order/validation-failed` | validateOrder limits exceeded, or exception | `{order: OrderDTO, failingDiscountIds: [UUID]}` |

- Timestamps are `OffsetDateTime.format(ISO_OFFSET_DATE_TIME)` of the **in-memory** entity. Create keeps the client's
  offset and precision. Update mixes values read from the DB (the R2DBC session offset, UTC in the containers) with
  input values.
- `OrderDTO` is the inbound order **re-serialized**: `{id, userId, createdAt: String, orderStatus: PENDING|PLACED|REJECTED,
  placedAt: String, rejectionReason?: INVALID_ORDER_DATA|INVENTORY_RESERVATION_FAILED, orderItems: [{id, createdAt,
  productVariantVersionId, productVariantId, taxRateVersionId, shoppingCartItemId, count: Long, compensatableAmount: Long,
  shipmentMethodId, discountIds: [UUID]}], shipmentAddressId, invoiceAddressId, compensatableOrderAmount: Long,
  paymentInformationId, paymentAuthorization?: {cvc: Int}, vatNumber?}`. Unknown inbound fields are dropped and nulls
  are omitted. Strings such as `createdAt` pass through unchanged.

### Consumed (programmatic subscriptions via `@Topic`; route = `/subscription/<topic>`; body = CloudEvent, `data` deserialized with Spring's ObjectMapper + Kotlin module, unknown properties ignored, missing non-null fields → 400)

| Topic | Route | Data | Handler |
|---|---|---|---|
| `user/user/created` | `POST /subscription/user/user/created` | `{id}` | `INSERT INTO UserEntity (id) VALUES (:id)` |
| `catalog/product/created` | `POST /subscription/catalog/product/created` | `{id, categoryIds: [UUID]}` | insert product, then one INSERT per `ProductToCategoryEntity` (**no tx**, partial writes possible) |
| `catalog/category/created` | `POST /subscription/catalog/category/created` | `{id}` | insert category |
| `catalog/product-variant/created` | `POST /subscription/catalog/product-variant/created` | `{id, productId}` | insert variant (no FK to product) |
| `inventory/product-item/reservation-succeeded` | `POST /subscription/inventory/product-item/reservation-succeeded` | `{order: OrderDTO}` | `validateOrder` (usages + result event in one transaction, Q2) |

All handlers answer `200` with an empty body. Any exception → 500 → Dapr redelivers (Redis Streams, no resiliency
policy, so it redelivers forever). Replication handlers are **not idempotent**: a duplicate event → duplicate key → 500
→ endless redelivery. **FIXED** (Q6): `ON CONFLICT DO NOTHING`, product + category links in one transaction.

**validateOrder**:
1. Group `orderItems` by each `discountIds` entry.
2. `findAllById(keys)`.
3. Compute remaining usages as in §6.3 (the same NPE for null `maxUsagesPerUser`). Discount ids unknown to the DB get
   `Long.MAX_VALUE`.
4. For each discount with `sum(count) > remaining`, add it to `failed`.
5. If `failed` is not empty → publish `validation-failed {order, failed}` and return 200.
6. Otherwise, for each discount, run the native SQL
   ```sql
   INSERT INTO DiscountUsageEntity (discount_id, user_id, usages) VALUES (:discountId, :userId, :usages)
   ON CONFLICT (discount_id, user_id) DO UPDATE SET usages = DiscountUsageEntity.usages + :usages
   ```
   then publish `validation-succeeded {order}`.
7. Any exception → publish `validation-failed {order, failingDiscountIds: []}`, **rethrow** → 500 → redelivery →
   another `validation-failed` per delivery. **FIXED** (Q2): rollback, one `validation-failed`, 200 (500 only if that publish fails).

The function does not check discount validity or applicability.

## 8. Persistence

Single migration `V1_1__create_relations.sql` (Flyway checksum **247510061**). It must be kept **byte-identical**, so
that the existing `flyway_schema_history` of the original DB validates.

Identifiers are unquoted camelCase, which Postgres folds to lowercase (`discountentity.maxusagesperuser`).

| Table | Columns |
|---|---|
| UserEntity / ProductEntity / CategoryEntity | `id uuid PK` |
| ProductVariantEntity | `id uuid PK, productId uuid NOT NULL` |
| ProductToCategoryEntity | `productId, categoryId, PRIMARY KEY(productId, categoryId)` (no FKs; V2: was `id` + UNIQUE) |
| DiscountEntity | `id PK default, discount float8, maxUsagesPerUser int NULL, validFrom/validUntil timestamptz, minOrderAmount int NULL` |
| CouponEntity | `id PK default, usages int default 0, maxUsages int NULL, validFrom/validUntil timestamptz, code varchar(255) UNIQUE, discountId FK` |
| CouponRedemptionEntity | `couponId FK, userId FK→UserEntity, PRIMARY KEY(couponId, userId)` (V2: was `id` + UNIQUE); BEFORE INSERT trigger `update_coupon_usages` |
| DiscountTo{Product,Category,ProductVariant}Entity | `discountId FK, <x>Id FK, PRIMARY KEY(discountId, <x>Id)` (V2: was `id` + UNIQUE), index on `<x>Id` (V3) |
| DiscountUsageEntity | `id, discountId FK, userId FK, usages bigint default 0, UNIQUE(discountId, userId)`; trigger `check_discount_usages` (raises when `usages > maxUsagesPerUser`) |

Later migrations of the port: `V1_2__user_indexes.sql` (indexes on `userId`), `V1_3__atomic_coupon_usages.sql`
(replaces `update_coupon_usages`, Q10), `V2__link_table_primary_keys.sql` (the five link tables get the pair as primary
key, the unused `id` column goes) and `V3__reverse_link_indexes.sql` (indexes on the second column of the three
`DiscountTo*` tables and on `CouponEntity.discountId`, used by the applicability query and the `discounts` connections).

The file has a stray `)` line after `DiscountUsageEntity`. Flyway 9.22.3 (original) and Flyway 13.10.0 (port) both
apply it, triggers included, with the same checksum 247510061. This was verified on 2026-10-13 against postgres:16
(Flyway 9 by hand; Flyway 13 in `DiscountIntegrationTest`). The port image also starts on a database that the
original's Flyway 9 migrated: the history validates and no migration runs.

## 9. Quirks and defects (originally preserved; fixed ones marked FIXED, see docs/fixes/discount.md)

- Q1 **FIXED** (docs/fixes/discount.md: the upsert now uses `discountId`/`userId`; works with and without the workaround). **The upsert uses snake_case columns** (`discount_id`, `user_id`) that do not exist. On a stock schema, every
  order with ≥1 discount id and no limit violation fails (validation-failed `[]` + 500 + redelivery forever). The
  calibration applies `architecture-optimization/cases/misarch/timing/calibration/workarounds/discount_usage_columns.sql`, which adds the
  columns, a unique index and a sync trigger. The port must send **the identical SQL**, so that it behaves the same
  with and without the workaround.
- Q2 **FIXED** (rollback + one `validation-failed` + 200). Any exception in validateOrder publishes `validation-failed` with an empty list **and** returns 500. Each
  redelivery publishes it again.
- Q3 **FIXED** (null = unlimited). `maxUsagesPerUser!!`: a discount with null `maxUsagesPerUser` (only possible through
  `updateDiscount(maxUsagesPerUser: null)`) makes `findApplicableDiscounts` (and so `createOrder`) fail for every
  matching variant. It also makes `validateOrder` fail.
- Q4 **FIXED** for the dataloaders (per-key `NoSuchElementException`). The dataloader NPE on an unknown id fails the whole batch. The stub `_entities` resolvers never check existence.
- Q5 Coupon validity is strict (`isBefore`/`isAfter`); discount validity in SQL is inclusive. Coupon validity and
  `maxUsages` are **not** checked in `findApplicableDiscounts` (only redemption by the user).
- Q6 Events are published inside the DB transaction (before commit). Replication handlers are non-idempotent, and the
  product handler is non-transactional. **FIXED** for the replication handlers (idempotent, product handler transactional).
- Q7 `hasNextPage` runs without ORDER BY. `first == null` → `LIMIT 9223372036854775807`.
- Q8 `DiscountUsage.usages` is a bigint, exposed as `Int` (`toInt()` truncation).
- Q9 `discountRequiresCoupon` returns nothing (not an error) without an `Authorized-User` header.
- Q10 **FIXED** (docs/fixes/discount.md: migration V1_3, one atomic `UPDATE … SET usages = usages + 1 … RETURNING`).
  `update_coupon_usages` reads `usages` without a lock and writes back `usages + 1`: concurrent redemptions of one
  coupon lose increments and can exceed `maxUsages`.

## 10. Migration notes (what the port does)

- **QueryDSL / infobip (kapt) → `libs/common` `Condition` + `BaseConnection` + `DatabaseClient`.** Each QueryDSL
  predicate became a SQL fragment with the same shape:
  - Connection joins → `INNER JOIN <LinkEntity> j ON ...` plus `j.`-qualified predicates.
  - The 3 applicability sub-selects, the "no coupons" `NOT EXISTS`, the "user has coupon" `IN`/`EXISTS` sub-selects,
    the validity window and the min order amount → `Condition` fragments over the main alias `t`.
  - `findApplicableDiscounts` runs its per-variant query through libs/common `ConditionQueries.findAll` (no ORDER BY;
    the ineffective `LEFT JOIN DiscountUsageEntity` is gone).
  - An empty coupon id list → `FALSE` (QueryDSL: `1 = 2`).
  - Derived queries (`findByCode`, `findByDiscountId`, `findByUserIdAndDiscountIdIn`) stay derived. Spring Data R2DBC
    handles the empty `In` set as before: an order without discounts validates.
  - The derived deletes `deleteByDiscountIdAnd<X>Id` became `deleteById(<key>)` on the composite primary key (same SQL shape).
  - Native SQL (`INSERT INTO ...Entity`, the upsert) is copied verbatim.

  Round trips per operation are unchanged. Two small differences: `hasNextPage` selects `1` instead of all columns,
  and `LIMIT` is omitted instead of `LIMIT 9223372036854775807` when `first` is null.
- **graphql-kotlin 7.0.2 → 11.0.0** (via libs/common): the federation spec is pinned to v2.5, the DateTime
  `@specifiedBy` is removed, and `clearDirectives()` is kept. `FederatedTypePromiseResolver`, `KotlinDataLoader`
  (`IdDataLoader`), `OptionalInput` and the `@GraphQLIgnore @Autowired` injection work unchanged. The connections now get
  an `R2dbcEntityTemplate` injected instead of a QueryDSL repository. java-dataloader 6 returns
  `CompletableFuture<out V?>`, so the entity resolvers call `.thenApply { it }`. `CommonOrder` now extends `BaseOrder`;
  the SDL is identical. `CouponFilter` needs the authorized user, so it is not a `BaseFilter`: `CouponConnection`
  combines it with the authorization filter in `authorizedUserFilter()`, evaluated lazily per field like the original
  `buildCondition()`.
- **Spring Boot 3.2.4 → 4.1.1, Kotlin 2.4, JDK 25**: coroutine `@Transactional` on the service methods (mutations,
  `DiscountUsageService.validateOrder`) works with the `R2dbcTransactionManager`. A failing upsert rolls back the earlier upserts
  of the same order (tested). `Mono.awaitSingle()` on a missing entity → explicit
  `NoSuchElementException()` without message, so the message is the same (`… : null`, verified on the running original,
  docs/INTEGRATION.md F3). All connections use `PagingValidation.QUERYDSL` (F2). Events are decoded with Jackson-2
  semantics for primitives (`fail-on-null-for-primitives: false`, F1): order's `{"cVC":123}` → `cvc = 0`, re-published
  as `{"cvc":0}` like the original. **FIXED** (docs/fixes/discount.md): `cvc` is read (alias `cVC`) and kept.
- **Dapr SDK 1.11 → 1.18.1 (subscriptions) + HTTP publish (libs/common `EventPublisher`)**: the `/dapr/subscribe`
  output equals `reference/dapr-subscribe/discount.json`. The payload JSON comes from `EventJson` (`NON_NULL`,
  declaration order), which is the same as the SDK serializer.
- `opentelemetry-javaagent.jar` comes from the template's base image instead of `src/main/resources`.

## 12. Deviations from the original

| Deviation | Reason | Expected effect |
|---|---|---|
| Events are published over the Dapr HTTP API (`POST localhost:3500/v1.0/publish/pubsub/<topic>`) instead of SDK gRPC | template-wide (docs/VERSIONS.md) | Same CloudEvent at the subscribers. Slightly different sidecar cost per publish (HTTP/1.1 vs gRPC) on the saga path (validation events) and on admin mutations |
| JDK 25 / Spring Boot 4.1 / graphql-kotlin 11 / Flyway 13 / OTel agent 2.32 | template-wide upgrade | Different JIT/GC and library CPU profile. No functional change observed |
| `hasNextPage` probe selects `1`; no `LIMIT` when `first` is null | `libs/common` `BaseConnection` | None functionally; marginally less data transferred |
| Empty coupon id list renders `FALSE` instead of QueryDSL's `1 = 2`; one coupon id renders `IN (?)` instead of `= ?` | `Condition.inList` | None (same plan class) |
| Join and sub-select aliases are `t`/`j`/`c`/`cr`/... instead of QueryDSL's `discountEntity`/... | hand-written SQL | None |
| `findApplicableDiscounts` runs without the original's `LEFT JOIN DiscountUsageEntity` | the join could not change the result | Same discounts; one join less per order item |
| The five link tables have the pair as primary key and no `id` column (V2); reverse-lookup indexes (V3) | natural key; index fixes (performance-visible) | None through the API; tools that write these tables directly must not insert `id`. Order validation and the `discounts` connections no longer scan the link tables |
| Transactions are on the service methods (`@Transactional`) instead of `Mutation` (`REQUIRES_NEW`) and a `TransactionalOperator` | one convention in all services | Same scope: one transaction per mutation and per order validation |
| DB error texts in GraphQL errors (unique/FK/trigger violations) come from Spring Data R2DBC 4 / r2dbc-postgresql 1.1.3 | library upgrade | Wording may differ slightly; the trigger messages (`Coupon has been used too often`, ...) are unchanged |

in the containers), as in the original. The tests force `-Duser.timezone=UTC` (build-logic) because the dev machine runs
